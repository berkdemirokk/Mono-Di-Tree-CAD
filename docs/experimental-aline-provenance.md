# Experimental A-line provenance: incomplete safety boundary

This is schema groundwork only. The A-line preview remains non-exportable and must not be transferred to CAD until every output and transformation boundary below is implemented and verified. The presence of `ExperimentalALine` identifies unapproved geometry; `ExperimentalOutputGuard` is an opt-in primitive, not a wired output lock. No production, fit or stitch approval is represented.

Version 10 records algorithm, request digest and front/back identity per piece. The digest identifies a request snapshot; it does not prove consent, source authenticity, bodily fit, or that current geometry still matches the original calculation. V10 may also include existing photo history; V0–V9 retain their previous shapes and validation. Older Windows/Apple readers reject V10 and must not silently strip its information. A future transfer needs an explicit format-upgrade warning and an independent compatibility review before it can be enabled.

Before transfer, define a durable and reviewable record binding both pieces to the original 11 values, unit, source digest, candidate method/version, four source and candidate ease values, assumptions, generated geometry and per-piece identity. Specify bounded size, validation and schema migration. An explicit approval to create an experimental draft is not a production clearance. Do not infer or automatically clear the experimental marker from changes to names, geometry or metadata. Any future release mechanism requires its own evidence, lifecycle and user-authorized review.

All derivations must preserve the restriction or reject the operation: duplication; transforms; split, join and closure; grading; nesting and generated copies; import/export projections; undo/redo; loading and saving. `PatternPiece.Clone` and document equality are covered here, but manual piece constructors elsewhere are not yet covered. Operations that create a new shape from mixed input must propagate the strongest restriction. The marker is not an authentication or tamper-resistant security boundary: manually editing a project file can remove it; output safety must not rely on untrusted file labels as proof of approval.

Wire a fail-closed check to every output, print, simulation and machine entry point, including direct format APIs and precomputed/prepared jobs, not only desktop dialogs. Review DxfFormat and DXF review exporters, SvgFormat, HpglFormat prepare/write, PdfFormat and tiled PDFs, machine center, SimulationQueue, selected-piece export and background job paths. Verify selected-output subsets explicitly and recheck immutable captured state at commit/write time. No silent strip, downgrade or regeneration of experimental state is allowed. Separately audit geometry provenance in all copy/transform/serialization paths and every supported Apple reader.

Only after those controls exist should transfer create both panels in one validated, bounded undo transaction, with explicit user confirmation, a current project/selection stamp, current source and candidate snapshot/revision checks before and after dialogs, and clear disclosure that these are incomplete lower sections. Tests must cover cancellation, reentrancy, stale targets, load/save/reload, old readers, all direct output paths, detached jobs, cross-piece transformations, and fail-closed behavior. Physical measurements and garment construction still require independent professional review and fitting.


## Detached candidate evidence, version 1 (not yet integrated)

`ALineCandidateEvidenceStorage` defines a separate `.tcad-aline-evidence.json` file. It does not change the V10 project format, existing V10 readers, or per-copy/nesting schemas. No CAD transfer, production, print or plotter permission follows from creating or loading it. No current UI writes or discovers this file. Keep it with the associated V10 project; the project does not contain a link to the sidecar, and missing evidence must never be interpreted as approval.

The record binds the request digest, two distinct piece IDs and their front/back roles, all 11 input values in millimetres, four original and four candidate ease values, algorithm and method version, fixed assumptions, and both ordered five-vertex panel geometries. The canonical SHA-256 uses domain-separated binary serialization: .NET GUID byte order, BinaryWriter UTF-8 strings, array lengths, and IEEE-754 binary64 bits in little endian. JSON is transport only. The source and result values are binary approximations, not exact decimal measurement preservation. The validator recomputes the restricted ease method and the two straight-edged candidate panels and rejects mismatched or out-of-range values. A recomputed hash detects accidental inconsistency; anyone able to edit the file can also recompute it, so it is not a signature, authentication, source proof, or proof of bodily fit.

`Matches` requires an externally supplied current request digest and 11-input/four-candidate values, plus exactly one matching closed front and back piece with the matching V10 experimental marker and exact ordered coordinate bits. A source change, field change, deletion, ID or side change, coordinate edit, translation or rotation makes the association stale; the marker and output prohibition remain. Reverting to the exact saved bytes can make this *content* comparison match again; it is not a monotonic revision check. Future UI/transfer code must additionally capture and recheck current source, form and project revisions before and after every confirmation. The v1 record deliberately describes the native preview coordinate system; placing or transforming panels needs a separately versioned, reviewed placement contract, not silent coordinate rewriting.

The file contains personal body measurements and derived geometry in unencrypted readable JSON. It contains only a digest of the request, not its text or photo; a digest is not encryption and may still be sensitive. It uses a new-file-only atomic write and rejects unknown, duplicate, missing or unsupported-version fields. Existing V10 projects remain loadable and unchanged; this sidecar is not a reason to upgrade the project format. Integrating the evidence into a project, proving two files are saved/recovered together, defining edit/revalidation UX, auditing all derivation and output paths and validating older readers remain open work. CAD/production/output gates must remain closed until those prerequisites and tests are complete.

Evidence records expose arrays to callers. Create, validation, serialization and matching capture bounded detached copies and then use only those copies; matching also captures both panel records. Callers must prevent mutation of the supplied arrays and document until capture completes. This is an operation snapshot, not locking or authentication. The evidence validator also reruns the original and candidate contour checks and the same segment mismatch bound as the candidate algorithm; boundary differential tests are required when either method changes.
V11 embeds the strict V1 candidate evidence in the same project envelope, plus four binary64 translations and the two resulting point sets, covered by a domain-separated SHA-256 digest. Coordinates are recomputed and compared bit-for-bit; translations that lose round-trip precision and overlapping bounding boxes are rejected. The digest detects accidental or unsophisticated alteration; it is not a signature or approval. Existing V10 files remain V10; readers that only support V10 must reject V11. The embedded evidence contains personal measurements in clear text. Project editing can make the evidence stale; a matching result is not approval, and all output guards remain mandatory. Callers must prevent mutation during capture. CAD transfer is not enabled: actual target collision/capacity, user consent and one-undo integration remain to be designed and independently verified.

Undo capacity also charges each embedded evidence record in geometry-equivalent 16-byte units, including its text and arrays with conservative fixed overhead; this is an estimate rather than a global managed-memory limit. File reads and encoded writes remain limited to 64 MB, while each embedded candidate is bounded to 16 KiB and the V11 list to 128 entries. The pairwise bounding-box rule rejects overlaps and touching between the two recorded panels. It does not check either panel against pre-existing CAD pieces; a future transfer must separately check its complete, stable target snapshot before it can be enabled.

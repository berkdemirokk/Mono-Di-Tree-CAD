# Namespaced project envelope: design for review

Status: **design and legacy-shape experiment only**. No production reader, writer, extension, registry entry, migration, or recovery change is implemented here. The existing version-10 write and recovery gate remains unchanged. No real project data or device is required.

## Problem and options

The physical and photo branches independently used numeric version 8, and no local scan can prove that numeric version 10 is globally unused. The existing desktop reader accepts either an unversioned project object or a two-element numeric-version array. The reviewed iPhone integration readers at `c63cf413` and `89a9376` accept an unversioned object or a two-element array with a recognized numeric version. Their dictionary fallback treats the object as legacy version 0; with `Name` and `Pieces`, unknown root fields can therefore be ignored during preview. The older checked-in iPhone viewer has the same structural risk. Adding a marker to a legacy-looking project object is not a safe format boundary for those viewers.

The iPhone observation is about potentially incomplete preview interpretation, not a finding that export deletes unknown fields. The independent source review indicates raw export preserves `sourceData` and the existing rename workflow preserves bytes outside the intended name edit; verify those claims on the actual supported build and file-provider paths before relying on them.

| Option | Benefit | Unresolved problem |
| --- | --- | --- |
| Reserve another integer in an internal registry | Smallest change to current files | Local scans and registry governance cannot establish what all deployed or unavailable readers assigned; old unknown readers may accept the integer with different meaning. |
| Add a marker beside legacy `Name` and `Pieces` | Familiar JSON object | The reviewed older iPhone viewer can interpret it as an unversioned project while ignoring the marker; an unreviewed reader may silently lose fields. |
| Wrap the project in a marker-bearing object without top-level `Name`/`Pieces` | No numeric-version collision; known old object reader lacks required fields | A permissive unknown reader could still interpret a wrapper unexpectedly; every old reader and raw-file workflow needs testing. |
| Use a three-element namespaced array with its own schema version | Distinct root shape; known legacy desktop and reviewed iPhone parsing paths require a two-element array and reject this shape | Old readers cannot edit or preview it; unsupported readers, import/export paths, file associations and recovery still require verification. |
| Add a binary magic header and separate extension | Strong boundary from ordinary JSON parsers | Breaks ordinary JSON tooling, importers, file association and the current recovery embedding unless separately redesigned; a header or extension alone is not an authorization or integrity proof. |

Recommend investigating the three-element array, with a fixed format-family identifier and an independently numbered schema, before making any production allocation. It reduces reliance on a globally unused integer; it does **not** prove that every unknown reader fails closed.

## Proposed shape and identity

```json
["urn:uuid:<approved-fixed-format-family-uuid>", 1, { "Name": "...", "Pieces": [], "GradingRules": [] }]
```

The placeholder is intentionally not an allocation. A randomly generated version-4 UUID could serve as a format-family identifier, but must be selected once, checked and recorded by the format owner, then frozen in code and compatibility fixtures. UUIDs make accidental collisions highly unlikely; they are not mathematical proof of global uniqueness, an authenticity signature, or permission to trust the payload. Do not generate a new family UUID per file, accept the synthetic fixture UUID as a production reservation, or silently change identifiers later. [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html) defines UUIDs and their URN namespace.

The second array element is the namespace's own positive integer schema version, independent of legacy numeric versions 1–9. The third is a complete project object, with explicit schema rules for physical identities, photo history, version-7 rotation history, and their allowed combinations. It is not a nested `[10, project]` envelope. Whether to use a separate extension is a product and platform integration decision; an extension is not a security boundary. Do not claim iPhone support based on the extension.

JSON permits arrays and objects but does not make field semantics safe by itself. Require the expected array length, exact family identifier and supported schema version; reject unsupported identifiers or versions without fallback to legacy parsing. The application must reject duplicate keys, unknown fields, malformed numbers and partial nested data even though a general JSON parser may accept some of them. Define and test the new writer's UTF-8 encoding and size limits without changing legacy UTF-8/UTF-16/UTF-32 handling. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) describes the JSON interchange format. An identifier is a contract label, not a requirement to fetch a schema or make a network request; [JSON Schema's identifier guidance](https://json-schema.org/understanding-json-schema/structuring) likewise does not require an identifier to be network-addressable.

## Reader, writer and migration requirements

1. Parse and fingerprint one immutable byte snapshot. Distinguish legacy numeric forms, unversioned legacy objects and the new namespaced form before model deserialization. Replace the current numeric-only `ProjectLoadResult.FormatVersion` and UI `fileFormatVersion` assumption with a typed family-and-version descriptor obtained from that same snapshot. Never reinterpret a namespaced schema version of 1 as legacy numeric version 1.
2. Keep the existing unambiguous v8 physical/photo discrimination, strict v9 photo-plane validation and legacy v1–v7 behavior. A raw numeric-v10 file remains unverified: reject it by default unless a separate, provenance-backed investigation establishes its exact origin and a safe explicit import path. Do not assume its number means this prototype's schema.
3. Validate all nested fields and limits, exact physical edge ownership and uniqueness, V geometry, frozen photo algorithms, rotation trace and project-wide constraints. Duplicate, null, empty, unknown, ambiguous, malformed, oversized or unsupported data must stop the read; never remove a field to make it parse. Historical photo records may legitimately outlive the corresponding visible piece.
4. Enable a new writer only after the marker is formally allocated and the complete release tests pass. Before committing, validate, serialize, re-read the candidate with the new reader and compare every persisted field against an independent model oracle. A marker is not evidence that a V feature was detected or that a design is fit for production.
5. Migration from legacy v8/v9 requires explicit user consent and a final review of source and a **new, nonexistent** destination. Preserve the original; reject same-file/hard-link aliases and existing destinations. Recheck the document and source snapshot after dialogs, keep the source safely open during the write, and use the existing fail-if-exists/compare-and-swap commit. Cancel, failure or a newly appeared destination must not modify either existing file. Do not automatically rewrite on open.
6. The current recovery envelope embeds a full project JSON value. Define how the new namespaced value is embedded, strictly validated and re-read without interpreting it as legacy numeric v1. Old recovery readers must not overwrite or delete unsupported snapshots. Check byte budgets, cancellation and warning states. Keep the current gate and honest “saving and recovery unavailable” message until all of this works.
7. Inspect every save, Save As, copy, background recovery, import/export, crash-recovery, and mobile file-provider path. The new extension or marker must not create a raw-copy, downgrade, or filename-alias bypass. Preserve explicit user consent and never overwrite a user file during testing.

## Evidence and tests required before enabling

- `scripts/TestEnvelopeLegacyRejection.ps1` is a read-only **synthetic shape experiment** against caller-provided old reader harnesses. In the recorded local run, the actual physical reader at `8f2df87` and photo reader at `d8a1ea6` each accepted legacy v1 and unversioned controls, rejected five unsupported shapes including the namespaced three-element array, and did not change fixture bytes: 14 reader/fixture combinations passed. Their rejection of an unknown marker on a legacy-shaped object does not establish the same behavior for the reviewed iPhone reader. The test UUID in that script is not approved for production.
- Build a real new parser/writer in a separate worktree and exercise all legacy v1–v9 fixtures, both distinct v8 forms, v9 plane data, a complete namespaced combined fixture, photo-only, physical-only, both together and combinations with version-7 rotation trace. Use hand-reviewed independent field, geometry, identifier, provenance and byte oracles; do not rely only on a serializer comparing its own output to its own reader.
- Against actual historical desktop binaries, assert old own-format acceptance with complete fields and reject new envelopes without altering input. Run actual iPhone tests on the supported build, including document-picker import, preview, storage, name/point editing, export, raw recovery, iCloud/file-provider behavior, and unchanged unsupported bytes. Static source analysis is not an iPhone execution test.
- Reject unknown family UUIDs, unknown schema versions, wrong array lengths and element types, nulls, numeric impostors, escaped keys, duplicate keys at every level, unknown nested members, invalid GUIDs and ownership, broken photo data, unsupported rotation history, malformed encodings and all size/count limits. Verify that no failure falls back to legacy object or numeric parsing.
- Exercise source/target aliases, hard links, stale source, target-appears races, cancellation at each stage, failed write/readback, old and new recovery coexistence, undo/redo, edits during dialogs and post-commit errors. Check original and destination bytes after every branch and use only synthetic files.
- Formally review the identifier, ownership and version policy across all maintained branches, distributions and platforms. Complete an independent security/correctness review. Keep both existing numeric-v10 and new-envelope production writes disabled until the release owner accepts that evidence.
